# Agent Note: 代理组收敛 — 61 组降到 11 组

Status: implemented

## Problem

用户原话:
> 「代理组只需要有个位数...最多是一个订阅，是属于一个代理组的，这是没问题的。然后一个住宅代理的服务商，一个代理组，这是没问题的」
> 「它为什么要傻逼傻逼的每一个订阅里面的每一个节点，它分别归类成一个单独的代理组呢？」
> 「太麻烦了，全部从全部删掉 反正就这么一点东西，重新建没写呢，搞那么麻烦」

实测生产库的形态 (收敛前):

| 项 | 数量 |
|---|---|
| 代理组 | **61** (其中 57 个是 `strategy=manual` 的单节点组) |
| listener | **78** |
| 订阅 | 4 |

**根因**: 57 个单节点组只钉了 28 个不同节点 —— 同一个节点最多被建了 5 次组
(如 `[良心云] 香港专线01` 被 `probe0` / `hk01` / `f0` / `watch0` / `gh-hk01` 各建一次)。

而服务端**早就提供了更合适的形态**, 且同库已有正确样板:
`良心云` 组用 `subscription_ids` **一个组覆盖 41 个节点** —— 但没有被推广。

原因在调用侧: `SourceSpec` 有 11 个字段 (`SubscriptionIDs` / `NameKeywords` / `Regions` /
`MaxLatencyMS` / `Limit` / `SortBy` ...), 而 57 个组**只用**了 `NodeIDs`。
`NameKeywords` 这类"按名字筛选"的字段就是为这种场景设计的, 实测无人使用。

## Decision

**全部删除, 用正确形态重建。**

1. **删**: 55 个无引用组 + 70 个 listener (全 HTTP 204)。删 listener 在前 ——
   `service.go:216` 的 `referencedBy` 会让"被引用的组"删除返回 409。
2. **保留 6 个组**, 正好符合用户的分组原则:
   `良心云`(整个订阅) / `residential-WsPxy-colo`(住宅服务商) /
   `ioa-vm` / `outlook` / `AI-演示组` / `gh-resi-clean`
3. **重建 5 个地区组**, 每个都是"引用订阅 + 关键字筛选 + 只要健康":
```json
{
  "name": "ghreg-jp",
  "strategy": "url-test",
  "source_spec": {
    "subscription_ids": ["sub-90fc407e8d5ce1fc95dc1a97ac7d927d"],
    "name_keywords": ["日本高速"],
    "states": ["healthy"],
    "sort_by": "latency"
  }
}
```
   **1 个组覆盖该地区全部健康节点**, 而不是每节点一组。

## Alternatives considered

- **逐个迁移 (把 listener 从单节点组改指向订阅组)**: 否决。用户明确"太麻烦了...重新建"。
  而且逐个迁移会保留 57 个组的残余语义, 不如删光重建干净。
- **保留单节点组但合并重复的**: 否决。真正的问题是"用 NodeIDs 逐节点建组"这个**形态本身**;
  合并只减少数量, 不改变形态, 下次还会长回来。
- **服务端加"listener 直指节点"能力, 然后删所有组**: 部分采纳 —— 那个能力**正在实现中**
  (另一 agent 在做 listeners 表加 `node_id` + 版本 38 迁移)。但本次不等它: 生产库的
  61 个组是既成事实, 先收敛; 能力到位后可进一步把地区组也省掉。
- **什么都不做**: 否决。61 个组让"哪个组是活的"无法回答, 且与用户的分组原则直接冲突。

## Consequences

**结果**:

| 项 | 收敛前 | 收敛后 |
|---|---|---|
| 代理组 | 61 | **11** (6 保留 + 5 新建) |
| listener | 78 | **18** |

**实测**: 粘性保持 —— 同一用户名连测 4 次出口完全一致 (`209.9.202.102`),
"注册全程同 IP" 的硬需求未受影响。

**一次操作事故 (已修复, 记录以备后人)**: 删 listener 时打断了 gh-registrar 的出口池 ——
它的 9 个 `ghreg-*` 用户名全被删, 一度 `healthy: False`。**教训: 删之前应先查产线依赖,
而不是删完才发现。** 已重建 9 个 listener 恢复 (实测 `healthy: True`, 出口 `23.237.50.27`)。
